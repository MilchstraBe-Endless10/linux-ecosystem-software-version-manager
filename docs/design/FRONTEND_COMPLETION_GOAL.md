## 4. 工作循环与提速方法

在同一目标内连续执行：读取当前证据→定位真实原因→批量处理同一区域相关缺陷→增量构建→正式 QML 渲染→对照截图→针对性测试→记录并选择下一项。不能只输出改进建议或每修一个控件即结束。不要为了跑测试重复全量编译：先用增量构建及相关测试，合并一组视觉修改后统一跑完整 Release 和 CTest，最终交付前全量验证。编译并行度按实际内存/临时空间决定，避免重现已知配额问题。先定位最影响构图、遮挡、真实数据和交互的缺陷，再做细节。

建立可重跑的本地视觉检查脚本或沿用现有脚本：固定分辨率、相同合成模型和动画相位，导出真实生产 QML 截图；保留原图与输出的并排/透明叠加及局部区域差异。用几何断言自动检查面板交叠、控件可见性、裁切、最小触控/点击区域和资源加载；用人工/视觉模型判读美术差距。不能人为选一个整体像素百分比作为合格线，不追求不同实际数据文字像素相同，不通过隐藏差异使指标好看。

若客户端支持子代理且本地权限允许，可将只读资产审查、视觉差异检查、测试诊断并行分配；独立文件的实现才可并行写入。正式 Main.qml/公共组件由同一集成负责人串行合并，禁止多个代理在脏工作树同时改同一文件。没有子代理仍应直接推进，不等待安装工具。不要创建无关 issue 或引入另一套框架。

如果一项被阻塞，记录具体验证过的原因、影响范围、可替代方案及需用户决策，转做其他无依赖项。缺少一项美术软件、真实候选、GPU 或原生授权不是所有工作停止的理由；不能反复试相同失败方式。停止修复某项必须有事实依据；不把仍可处理的视觉问题当成外部阻塞。
